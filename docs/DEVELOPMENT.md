# 珠珠与小花 · 私人健身 Agent 开发文档

版本：v1.2  
初版日期：2026-09-01  
修订日期：2026-09-02  
状态：开发规格，尚非已实现或已部署的软件  
读者：项目维护者、负责实现的 Coding Agent

> 一个供珠珠和小花共同使用的私人 Web App。页面展示每天的饮食和训练；Agent 通过对话维护计划、日志与长期记忆，也能修改前端。业务状态存文件，历史交给 Git，服务部署在自有 VPS。

本次修订：保留图片上传与理解的完整链路，将联网服务统一为 Exa Search + Contents，并补齐每月免费额度优先的配置、用量保护、失败处理和验收。仍然只有两个主要页面、一个服务、一个 Agent 和文件/Git 存储，不增加第二家搜索服务、数据库或计费平台。本文是整合后的完整规格，可直接替换旧版。

## 1. 已确定的方向

| 决策 | v1 采用的方案 |
| --- | --- |
| 用户 | 珠珠 `zhuzhu`、小花 `xiaohua`，两个平等账号 |
| 主要页面 | 今天、Agent；不建设传统后台 |
| 主要编辑入口 | Agent 对话，辅以少量快捷操作 |
| 前端 | React + Vite + TypeScript，聊天复用 assistant-ui |
| 服务端 | 一个 Node.js + Hono 服务 |
| Agent | 复用 Pi SDK，不自行实现推理循环和会话压缩 |
| 图片 | 聊天附件上传、受保护读取、传给支持图像输入的模型 |
| 联网 | Exa Search + Contents，两个服务端工具；优先覆盖在每月免费额度内 |
| 状态 | JSON 业务文件、Markdown 动作说明、SDK 会话文件 |
| 版本管理 | 应用代码、个人数据分成两个 Git 仓库 |
| 记忆 | 当前档案 + 三份长期记忆文件 + SDK 会话 |
| 修改界面 | 在独立 worktree 修改，沙箱检查，预览后发布 |
| 部署 | 一个常驻应用服务；代码检查使用临时无根容器 |

本项目不是健身 SaaS、通用 Agent 平台、在线 IDE 或低代码搭建器。

### 1.1 Ponytail 在本项目中的含义

Ponytail 的核心不是把代码挤成一行，而是理解现有流程后，优先省略不需要的功能、复用已有实现、使用标准库和平台能力，最后才新增最小必要代码；校验、安全、错误处理和无障碍不能为此删除。[S1]

本项目据此固定以下取舍：

- 不用数据库服务、Redis、向量库、多 Agent 编排、MCP 服务、事件总线、插件市场。
- 不建设通用记忆引擎、通用文件数据库、动态表单引擎或页面配置 DSL。
- Git 已经记录历史，不再给每条记忆另外实现完整事件溯源。
- 普通数据修改直接执行；前端发布只保留一次明确确认，不做多级审批。
- 必须保留身份识别、路径限制、文件校验、防重复写入、真实执行回执和可恢复发布。

增加任何依赖或抽象前，先回答：当前哪一个已确定场景不能由现有实现完成？不能回答就不加。

## 2. 用户、共享范围和初始化

### 2.1 固定身份

内部主体只使用：

```ts
type PersonId = 'zhuzhu' | 'xiaohua';
type MemorySubject = PersonId | 'shared';
```

界面统一显示“珠珠 / 小花 / 两人”。`shared` 仅代表共同偏好或共同安排，不是一位可以记录体重、摄入量或训练重量的第三用户。

后端根据登录会话生成 `actor`。页面上正在查看“小花”，不能把珠珠的登录身份改成小花。“帮我记录”指当前登录者；“帮小花记录”指明确命名的主体。人物不明确时只追问这个必要问题。

所有记录保留 `subject` 和 `recorded_by`，两者可以不同。Agent 的成功回执明确写出人物和日期。

### 2.2 v1 的共享约定

两人首次登录时确认：本应用中的档案、计划、饮食训练日志和长期记忆对两人共享，允许互相代记。双方拥有相同的业务权限。

聊天线程各自保存，默认只展示、检索当前账号的原始对话。进入共享长期记忆的信息对两人可见。v1 不做逐条隐私权限、组织角色或邀请管理。

附件默认仅上传者可读；用户要求将图片用于共享日志或计划、并成功保存附件引用后，两人可通过该记录查看这张图片，不因此开放原始聊天。上传、引用和读取都由服务端验证，不允许通过猜测附件 ID 越权。

### 2.3 现有信息不能未经确认直接导入

当前对话已经确定两个人的称呼，但尚未明确前面两份身体资料分别属于珠珠还是小花。初始化只建立两个名字和 ID，其余未知字段填 `null`。

导入历史方案前，由两人确认资料归属、基本信息、目标、训练经验、器械条件及饮食限制。此前对话中的示例重量、推测性健康数据、建议时段不能当成已发生的日志或已确认的个人偏好。

空系统应显示“尚未确认计划”，不能生成虚假的完成记录。开发演示数据只放在测试 fixtures 中，不进入真实数据仓库。

## 3. v1 的用户体验

### 3.1 今天

页面提供日期选择，以及“珠珠 / 小花 / 两人”的查看筛选。日期选择优先采用原生日期控件。

页面展示：当天训练类型、动作顺序、两人各自的组次目标与实际记录；早餐、午餐、晚餐、加餐的具体安排和份量；已记录营养合计；未记录或部分记录状态。

动作展开后显示器械设置、步骤、注意事项和替代动作。手机上纵向排列两人的数据，桌面有空间时并排；不强行把宽表格挤进窄屏。

首页直接读取文件快照，不调用模型。模型服务不可用时，已经保存的计划和日志仍可查看。

首页不建设通用编辑表单。可以保留“记录一组”“按这餐吃了”等按钮，但它们只是把带有人物、日期和条目引用的文本送入同一个 Agent 入口，不另建一套独立写入逻辑。

### 3.2 Agent

复用 assistant-ui，提供消息、流式输出、停止、工具回执、新会话及图片附件。手机切换页面，桌面可展示侧栏；无需独立聊天产品的完整会话管理功能。

输入框支持选择图片及缩略图预览，桌面支持粘贴图片；手机使用系统文件/照片选择器。发送前可以移除附件，上传失败允许重试，不把失败附件悄悄丢弃后仅发送文字。上传未完成时禁用发送；图片已上传但尚未发给 Agent 时不调用模型。已发送消息刷新后仍能显示附件。

搜索与阅读沿用普通工具回执，显示查询或网页标题、状态和来源链接。接近本地月度预算时在 Agent 页显示一句提醒，达到上限则说明暂停联网；不新增研究页面、账单页面或专门的搜索组件系统。

只定制两类工具卡片：

| 卡片 | 内容 |
| --- | --- |
| 数据修改 | 人物、日期、简短改动、保存状态、Git revision |
| 界面修改 | 当前阶段、检查结果、预览、发布、继续修改 |

“已保存”“检查通过”“已发布”来自服务端状态，不能由模型自行生成一个绿色成功标记。

不默认展示完整命令输出、服务器路径或所有工具参数；需要排错时再展开经过脱敏的详情。

### 3.3 非主要页面：恢复入口

保留一个由服务端提供的简单 `/ops` 页面，使用相同登录保护，显示当前前端版本及回滚操作。它不依赖 Agent 可修改的 React 代码。

这不是后台管理平台，只是防止前端改坏以后连发布和恢复入口也一起消失。

## 4. 架构与依赖

```text
浏览器
  ├─ 今天：读取已提交的数据快照
  └─ Agent：发送消息、接收流式事件
                 │
        Node.js / Hono 服务
          ├─ 登录与人物识别
          ├─ 单任务队列
          ├─ Pi SDK 会话
          ├─ 受控文件读写与 Git
          ├─ 图片校验与模型附件、Exa 搜索/阅读
          └─ 前端检查、预览和发布
                 │
          ┌──────┴────────┐
       data-repo       app-repo
      计划/日志/记忆     前端源码
                         │
                    独立 worktree
                         │
                    临时构建沙箱
                         │
                    不可变发布产物
```

### 4.1 依赖选择

| 用途 | 选择及限制 |
| --- | --- |
| 前端 | React、Vite、TypeScript；不另外引入大型全局状态库 |
| 聊天 | `@assistant-ui/react`，通过 ExternalStoreRuntime 对接后端 |
| 后端 | Hono 及 Node 适配器；路由、Cookie 等优先复用其现有能力 |
| Agent | Pi SDK；只写本应用所需的工具和事件适配 |
| 图片 | 复用 assistant-ui 附件适配；服务端用 sharp 校验与规范化，不自写图片解码器 |
| 搜索/阅读 | 同一 Exa 服务的 Search / Contents；Node 原生 fetch 调用即可，不额外引入服务商抽象层或 MCP |
| Schema | 沿用 Pi 工具使用的 TypeBox，统一文件与接口校验，避免再引入第二套 Schema 系统 |
| 测试 | Vitest；前端关键流程使用 Playwright |
| 沙箱 | rootless Podman，使用维护者准备的固定构建镜像 |

assistant-ui 的 ExternalStoreRuntime 支持接入外部消息状态和工具结果，因此不要求同时引入 Vercel AI SDK 或 assistant-ui 的托管服务。[S2] Hono 可以通过 Node 适配器运行，并提供静态文件服务能力。[S3]

核对时 Pi 官方仓库已跳转到 `earendil-works/pi`，当前文档包名为 `@earendil-works/pi-coding-agent`；不要直接沿用旧资料中的包名或接口。其 SDK 提供会话、流式事件、自定义工具和文件持久化。[S4][S5]

不在文档中假定某个主分支版本已经验证可用。初始化时检查实际发布包、Node engines 和 SDK 示例，完成最小接入测试后锁定版本。提交 `pnpm-lock.yaml`、`packageManager` 与 Node 版本约束；部署使用冻结 lockfile，不自动跟随 `latest`。

### 4.2 工程结构

一个应用仓库、一个 package.json 即可，不用 Turborepo，不预建大量空包。

```text
app-repo/
├── web/
│   ├── src/                    # 页面、组件、样式
│   └── public/                 # 可审核的静态资源
├── server/                     # API、Agent、文件保存、发布
├── shared/                     # 数据契约及纯计算函数
├── tests/                      # 契约、恢复和浏览器测试
├── AGENTS.md
├── docs/DEVELOPMENT.md
├── package.json
└── pnpm-lock.yaml
```

按职责拆文件，但没有复用就不预建 repository、service、manager、factory 等层级。`server/agent.ts` 只适配 Pi，不抽象一个“可切换任意 Agent 框架”的平台。

## 5. 文件与数据契约

### 5.1 通用规则

结构化文件带 `schema_version: 1`；编码为 UTF-8，JSON 使用两空格缩进和末尾换行。ID 创建后稳定，不使用显示名称或数组下标作为记录身份。

所有日期按应用配置的时区解释，默认 `Asia/Shanghai`。事件保存带时区的时间戳，同时保存所属业务日期。当前时间和“今天 / 昨天”的解释由服务端提供，不能依赖模型自己的日期。

缺失数据用 `null` 或明确的未记录状态，不以 `0` 代替。生重、熟重、每只哑铃、杠铃总重等单位必须明确；暂时不知道就标为未知并追问，不悄悄换算。

下述字段是需要实现的契约，不要求预先搭建一个通用 Schema 注册系统。实际 Schema 只维护一份，从中导出 TypeScript 类型，前后端共用。

### 5.2 档案：`people/{person}.json`

| 字段 | 含义 |
| --- | --- |
| `person_id`、`display_name` | 固定主体与名称 |
| `height_cm` | 已确认身高，未知为 null |
| `age_at_confirmation`、`confirmed_at` | 可选；不强制收集完整生日，也不把年龄永久写死 |
| `training_experience` | 已确认的训练经验 |
| `goal` | 用户确认的目标说明；目标体重可选 |
| `constraints` | 用户明确报告的饮食、训练限制及来源 |

首次只填姓名与 ID。目标属于档案；某天应吃多少、练多少属于计划；实际体重属于日志。不要把同一个事实同时维护在三处。

### 5.3 每日计划：`plans/{date}.json`

v1 直接保存按日期展开的计划。Agent 一次可以生成未来七天，不建设重复规则引擎、模板继承系统或自动排课系统。

| 字段 | 含义 |
| --- | --- |
| `date` | 计划日期 |
| `status` | `draft` 或 `active` |
| `title` | 共同主题，例如“上肢 A” |
| `people.zhuzhu`、`people.xiaohua` | 两人的具体计划 |
| `people.*.nutrition` | 当日营养目标及各餐食物、份量、单位、估算来源 |
| `people.*.training` | 训练类型、动作序列、各自组次目标、休息时间、可选有氧 |
| `notes` | 变更原因、临时限制等 |

两人的训练默认同一主题和顺序，但各自保存目标组数、次数区间和负重建议。直接重复少量结构比实现“共同模板 + 多层覆盖”更简单。

每餐至少列出食物和份量；每个动作至少包含稳定的 `exercise_id`、名称、正式组数、次数目标、休息秒数和注意事项引用。有氧则记录方式、时长和强度描述，不强行套用力量组次字段。

临时只有一个人休息时，明确写入该人的计划，不为了同步把另一人的训练也标记为休息。修改未来计划默认不改历史日期。

### 5.4 实际日志：`logs/{date}/{person}.json`

建议形状如下；这只是空记录结构，不是真实数据：

```json
{
  "schema_version": 1,
  "date": "2026-09-01",
  "person_id": "zhuzhu",
  "plan_revision": null,
  "nutrition_status": "unlogged",
  "meals": [],
  "training_status": "unlogged",
  "sets": [],
  "cardio": [],
  "measurements": [],
  "notes": []
}
```

`plan_revision` 指向当时引用计划所在的 data-repo commit。以后计划改了，实际日志仍能回看当时的安排。

| 条目 | 最少保存内容 |
| --- | --- |
| 餐食 | ID、餐次、食物和份量、已知营养值或 null、估算依据、实际发生时间 |
| 力量组 | ID、动作、器械标识、负重及口径、次数、左右侧、热身/正式组、可选余力 |
| 有氧 | ID、活动方式、实际时长、可选强度描述 |
| 测量 | ID、测量类型、值、单位、测量时间 |
| 来源 | `recorded_by`、`request_id`、原始输入引用、记录时间，由服务端补齐 |

“计划吃了”与“已经吃了”分开；未记录不等于没有吃。营养记录完整度使用 `unlogged / partial / complete`，完整状态由用户说明或明确确认，不能仅因为存在一条记录就判断全天完整。

营养合计只统计已记录且有数值的条目；存在未知值时显示“已知合计，尚有未估算项”。未记录日期不能按零纳入平均摄入。训练进步比较必须采用相同动作、器械和负重口径。

程序负责加总、平均和日期筛选。Agent 提供分析文字，不自行制造统计数字。v1 的体重摘要显示“最近七个自然日中的 n 天有记录”及这些有效数据的平均值，不把不足七天的数据写成完整七日均值。

涉及图片的条目在来源中保存 `attachment_ids`，不保存服务器绝对路径或 Base64。餐食的 `value_kind` 区分 `label / weighed / estimated / unknown`，并保存 `assumptions`；称重并不等于用油和营养成分也精确。图中可读的测量数字按原值记录，无法读出的值保持未知。外部资料采用来源引用，不将整篇网页写进日志。

### 5.5 动作说明：`exercises/{exercise_id}.md`

每个文件包括：名称、器械设置、起始姿势、动作步骤、呼吸提示、常见错误、停止信号、替代动作、资料来源。

联网补充的资料来源至少包含标题、原始 URL 和查阅时间；发布日期未知就留空，不把抓取时间冒充发布日期。网页支持的是动作说明，不是珠珠或小花的个人身体事实，也不能自动变成长期偏好。

Markdown 用于阅读，不参与执行。前端禁用原始 HTML，不加载说明文件要求的脚本。不要使用模型生成图片充当已验证的动作教学。已有动作说明只在相关任务中修改，不每次聊天重新生成整套动作库。

### 5.6 UI 配置：`ui.json`

只存已经实现的少量选项，例如主题、训练/饮食显示顺序、紧凑模式。用枚举验证，不存任意 JavaScript、HTML、CSS 表达式或组件定义。

新增布局能力应该修改前端，而不是继续扩充一个通用页面配置语言。

## 6. 记忆：三个文件足够

### 6.1 职责分开

| 内容 | 唯一主要来源 |
| --- | --- |
| 身高、目标等当前稳定事实 | `people/` |
| 应当吃什么、练什么 | `plans/` |
| 实际做了什么 | `logs/` |
| 刚才在聊什么 | Pi SDK session |
| 长期偏好、约束、共同约定 | `memory/` |
| 为什么应用这样设计 | 本文档及 `AGENTS.md` |

不另建 facts、preferences、decisions 三套事件文件，不建设 memory-index，不维护浮点置信度，也不默认跑自动记忆巩固任务。

### 6.2 三份长期记忆

`memory/zhuzhu.json`、`memory/xiaohua.json`、`memory/shared.json` 都是一个小型记录数组：

```json
{
  "schema_version": 1,
  "items": [
    {
      "id": "example-memory-id",
      "key": "training.same_daily_theme",
      "text": "珠珠和小花希望每天训练相同部位，并分别调整重量和训练量。",
      "evidence": "explicit_statement",
      "source": {
        "actor": "zhuzhu",
        "request_id": "example-request-id"
      },
      "updated_at": "2026-09-01T23:00:00+08:00"
    }
  ]
}
```

以上 ID、时间和发言者仅演示格式，不能直接作为真实来源导入。文件名决定主体，避免重复维护 `subject` 字段。

新增和更新沿用普通受控文件提交；`key` 相同则更新现有条目，保留 ID。旧值由 Git 保存，不再追加 superseded 事件。

### 6.3 什么进入长期记忆

明确表达的持久偏好、约束、约定可以直接保存，例如“不安排周六训练”。某次训练重量、今天疲劳、午饭吃了什么进入日志，不进入长期记忆。

Agent 的建议不是用户偏好。尤其不能把“建议 17:30 训练”保存成“珠珠喜欢 17:30 训练”。从日志发现的模式先在回答中注明推断；用户确认后再保存，不把模型自评的高置信度当成确认。

查今天的训练先查计划，查最近表现先查日志，不让长期记忆覆盖最新业务数据。

### 6.4 检索与遗忘

每次对话加载当前账号档案和相关的活跃长期记忆；两人的共享数据只在任务需要时读取。超出轻量上下文时按 key 和关键词筛选，不优先引入 embedding。

用户要求忘记某个偏好时，从当前 memory 文件删除并提交。涉及的活跃会话不再携带旧偏好；共同记忆变更要处理两人的相关上下文。开启新 SDK 会话，只注入当前资料；原会话归档，不自动重抽取旧聊天恢复该记忆。

普通遗忘不等于物理删除。Git 历史、归档会话、附件和备份可能仍然包含原内容；永久清除属于维护操作，需要检查所有副本，不能只做一次普通 commit 就宣称彻底删除。

阶段复盘先按需生成。只有真实使用需要定时复盘时，再接系统已有定时器，不先建设调度平台。

## 7. Agent 接入

### 7.1 一个 Agent 身份，受控的两种任务

只使用一个人格和同一套 Pi 接入代码，不做营养师 Agent、训练 Agent、程序员 Agent 相互委派。

普通任务和 UI 任务使用同一个 Pi 会话。每轮创建一个受控工作区：`app/` 和 `data/` 是独立 Git 副本，`inbox/` 只包含本轮只读附件。代码任务按需读取数据，不默认把两人的完整健康日志塞进模型上下文。

这是工具范围和上下文隔离，不是多 Agent 编排。

### 7.2 会话和可信上下文

每个账号使用明确绑定的 SDK 会话文件。不要在两个用户共用的 cwd 中调用“继续最近一次会话”来推测归属。

每轮请求由服务端注入：当前 `actor`、当前时间与时区、请求 ID、app/data 基准 revision 和允许的工具。Agent 自行从工作区读取任务所需的当前档案与记忆。前端发送的 `actor`、模型自己声称的身份都不构成授权。

Pi 的默认 ResourceLoader 从工作区根目录正常加载宿主生成的可信 `AGENTS.md`。它不从 data、inbox 或生产上传目录加载可执行扩展、hooks 或工具。[S4]

`AGENTS.md` 中的设计说明只是开发上下文；运行时权限由程序控制，不因某个 Markdown 文件写着“允许访问密钥”就改变。

### 7.3 最小工具集合

优先使用 Pi `0.84.4` 的原生 Coding Agent 工具定义，将它们的执行后端转发到无网络的 rootless Podman。模型仍看到标准工具名和参数，不继承 Hono 进程的文件、进程、网络或密钥权限。

| 工具 | 用途 |
| --- | --- |
| `read/write/edit/bash/grep/find/ls` | 在隔离 app/data/inbox 工作区中浏览、编辑、运行 Git 与现有检查 |
| `web_search` | 查询公开资料，返回带原始 URL 的结果摘要 |
| `web_read` | 通过 Exa Contents 读取一个公开网页，返回正文和截断/失败状态 |

最终命名可以随实现调整，不再建设一个可扩展“工具市场”。发布由带身份验证的操作接口完成，不把生产部署命令直接交给模型。

Agent 直接编辑副本，不再用一组 CRUD 工具模拟文件操作。来源字段、请求 ID 和 Git 提交元数据仍由 Finalizer 生成或覆盖，模型不能伪造另一个人的操作身份。

### 7.4 操作权限

普通新增、纠正日志、维护记忆、修改用户明确要求的安排、修改已实现的 UI 配置可直接执行。完成后回执包含人物、日期和 revision。

无法确定人物、日期、关键单位，或出现大量删除、目标重大变更而用户意图不明确时，先澄清。对没有明确授权的持续性饮食和训练调整，先提出建议；用户明确说“以后改成这样”后直接提交。

Agent 可以自主写前端、反复修复检查错误，但 v1 发布需一次明确确认。不做 Safe/Auto/Dev 三套权限系统。

### 7.5 成功与失败的表达

模型不表述“已保存/已发布”；它只说明已修改工作副本。真实保存、预览和发布回执由模型结束后的宿主 Finalizer 生成。

食品照片的份量和营养值标记为估算；缺少记录时不推断用户没有进食。遇到疼痛或其他健康异常，不自动靠加训练量或压低摄入解决；应用不承诺诊断或专业医疗替代能力。

### 7.6 图片：从附件到模型的完整链路

assistant-ui 的附件适配器可接自己的上传接口，ExternalStoreRuntime 支持该适配方式。[S2][S12] Pi SDK 的 `session.prompt(text, { images })` 支持图像内容，但具体内容结构要以锁定版本为准，配置的模型也必须实际支持图片输入和本应用需要的工具调用。[S4] 只给模型一个附件 ID、网页地址或服务器文件路径，不算完成图片理解。

实现一条链路即可：选图 → `POST /api/uploads` → 获得附件 ID → 与文字一起提交消息 → 服务端验证附件权限并构造 SDK 图像内容 → 同一 Agent 理解并调用现有数据/代码工具。优先直接使用视觉模型，不叠加 OCR 服务或另一个图片 Agent。

| 环节 | v1 的具体要求 |
| --- | --- |
| 输入范围 | JPEG、PNG、静态 WebP；每条消息最多 4 张，每张最多 10 MiB、解码前限制 2000 万像素。这些是产品默认上限，不是模型能力承诺 |
| 手机格式 | 不支持的 HEIC、动图等给出明确提示，要求转为上述格式，不静默失败；不为 v1 建转码平台 |
| 校验处理 | 检查实际格式并成功解码，不信扩展名和客户端 MIME。使用 sharp 修正方向、按需缩放并重新编码，移除 EXIF 等元数据；保留标签文字的可读性。[S15] |
| 保存 | 服务器生成随机 ID；以 `uploads/{id}.{ext}` 保存规范化图片，`uploads/{id}.json` 保存 owner、MIME、字节数、宽高、哈希、创建时间。临时上传原件处理完即清理，不额外长期保留原件 |
| 请求 | 后端按 ID 从允许目录读取图片字节，构造模型图像输入；不要让模型提供待读取路径，不向外部服务开放私有附件 URL |
| 展示 | 消息保存附件引用，浏览器通过鉴权读取接口展示；移除未发送附件只从草稿移除，不删除已被其他消息/日志引用的文件 |
| 历史 | SDK 可能在会话中保存图像内容；按私密会话纳入配额、备份和清除范围。文件和会话都不进 Git，不强行重写 SDK 会话格式 |

输入校验不替代模型请求限制：规范化后的图片大小、单图限制及整轮请求总量也要按实际提供商约束校验。需要缩小或裁剪时明确提示，不能静默丢图或把数字压到不可读。旧图不在当前视觉上下文时，不以会话摘要冒充重新看过；用户可以从旧消息重新附带该图片。

模型不支持图片或图片调用失败时明确报错，保留输入与附件，不降级成“假装看过”的文本回答；用户可以改为纯文字或由维护者更换模型。只发图片、没有文字时允许询问用途，不自动把图片当作已吃、已练或今天测量。

实际场景：餐食照片可以估算并记录，包装标签用于按食用量计算，体脂秤截图用于读取明确的数值与测量时间，器械照片用于解释动作，参考界面截图用于本次前端修改。人物、日期、已食用量无法确定时只追问必要信息。看不清的数字不猜，照片估餐不伪装为精确测量；公式与加总仍由程序执行。

代码会话只接收本次 UI 任务明确提供的参考图；不把私人照片复制到 `web/public/`、Git、预览或构建沙箱。图片被模型查看不代表它要成为应用静态资源。

### 7.7 联网：Exa Search + Contents

Pi 的文件工具不等于公开网页搜索。由同一个 Node.js 服务注册两个自定义工具，只接 Exa Search 与 Contents。使用 Node 原生 fetch，不另加 Exa SDK、MCP、研究 Agent、爬虫、自动浏览器或多服务商切换层。[S13][S14]

| 工具契约（本项目定义） | 返回内容 |
| --- | --- |
| `web_search({ query })` | `results[]`：标题、原始 URL、相关片段；服务端 `retrieved_at`、可得的发布日期及失败状态 |
| `web_read({ url, fresh? })` | 请求及返回的 URL、可得标题、提取正文、`retrieved_at`、`truncated`；失败时返回具体错误；fresh 默认为 false |

调用固定的 `https://api.exa.ai/search` 与 `https://api.exa.ai/contents`，凭据通过服务端的 `x-api-key` 请求头传入。Agent 只能提交 query，或公开 URL 与可选的 fresh 布尔值；不能覆盖 endpoint、请求头、计价模式和批量大小。[S13][S14]

**固定请求形状。** 服务端完成参数校验后构造请求；下列是外部 HTTP body 的实现起点，不是需要用户填写的表单：

```json
{
  "query": "待查询的公开问题",
  "type": "auto",
  "numResults": 5,
  "contents": {
    "text": false,
    "highlights": true
  }
}
```

```json
{
  "urls": ["https://example.com/public-article"],
  "text": true,
  "highlights": false,
  "maxAgeHours": 24
}
```

Search 默认取 5 条相关片段，不额外请求 `summary`；片段不冒充已阅读全文。5 条是为了减少噪声与模型输入，不是声称在同一基础计费档内比 10 条更便宜。Contents 每次只读取一个 URL，只请求正文一种内容类型；不同时传 `ids` 与 `urls`，不请求 AI 页面摘要、子页面或额外内容类型。参数以接入时官方接口为准，必须通过真实接入测试。[S13][S14]

v1 不开放 `deep` 等深度模式、`/answer`、Exa Agent、Monitors 或合成答案功能。`type`、结果数量与内容选项由受信任服务端固定，不能通过工具参数透传开启额外计费功能。后续确有需要再由维护者修改，不先建选型菜单。

读取响应时检查 HTTP 状态与结构，Contents 还须核对对应 URL 的 `statuses` 和非空正文；HTTP 200、只返回标题或某个其他 URL 成功都不等于本页读取成功。保留可用的提供商 `requestId` 便于排错。401/403 明确报配置或权限问题；402 按额度/预算不足处理，429 按限速处理，不能全部包装成“没有搜索结果”。[S14][S21]

每次 HTTP 调用默认最长 20 秒，响应体最多 2 MiB；每条搜索片段最多传给模型 1,500 字符，单页正文最多 20,000 字符。单个 Agent 任务最多 6 次实际联网请求，所有尝试都计数。这些是本应用的默认保护值，不是 Exa 的限制。先限制读取字节，再截断正文；返回截断标记，不宣称截断文本就是完整网页。

同一任务内相同参数已经成功返回时，直接复用该工具结果。若已有内容足以支撑回答，不为走流程重复读取；任务之间不额外建设持久网页缓存。Contents 默认 `maxAgeHours=24`；核对最新内容时可令 `fresh=true`，由后端映射为 `maxAgeHours=0`，不使用已弃用的 `livecrawl`。参数改变即属于新的调用，也需检查预算。保留可得的缓存/抓取来源信息；`retrieved_at` 只表示本应用收到资料的时间，不证明页面在此时刚更新。即便新抓取也不代表网页内容必然最新，无法核实时明确说明限制。[S14]

请求取消时中止本地等待，失败不做透明的自动重试；取消或超时不保证上游未处理或未计费。新的尝试必须重新检查调用次数及第 7.8 节预算。工具结果复用原有 request/SDK 会话存储，不建立网页数据库或全文索引。

只问今天练什么、记录一餐、查询本地训练记录、调整页面间距时不强制联网。用户明确要求查找、核实或阅读网页，或任务确需更新的框架接口、官方食品信息、训练资料时再调用。软件优先查官方文档，健康训练资料优先查专业机构与原始研究；搜索排名本身不作为可靠性判断。

回答在相关结论后引用真实工具结果中的来源链接，区分相关片段和已读取正文；不伪造文章、作者和发布日期。来源沿用安全 Markdown 和工具回执，不加载外部缩略图。保存动作说明时附原始 URL 和查阅时间，不把网页内容当成珠珠或小花的长期个人记忆。

用户提供公开 URL 时可以直接阅读，不必先搜索；登录页、付费墙和无法提取的内容不绕过限制。失败或超额后允许继续本地查询和记录，也可提供明确标注的已有知识说明，但不能声称“刚刚查到”。本节联网仅属于受信任后端，不放开第 10 节构建沙箱网络，隐私与 URL 边界见第 12 节。

### 7.8 免费额度优先：用量保护，不做计费平台

**核对日期：2026-09-02。** Exa Free 当前每月提供 $10 额度、无需支付方式；新账号的一次性 $20 不计入长期容量规划。标准 Search 为 $7/千次（最多 10 个结果的基础档），Contents 为 $1/千页/内容类型；额外摘要及其他模式可能另收费。此处为当日政策记录，不是对未来永久免费或特定账号额度的承诺；上线时仍须核对官方定价与账号状态。[S19][S20]

以两人合计每天 10 个联网问题、每题 2 次标准搜索和 2 页正文、30 天为例：600 次搜索约 $4.20，600 页单类型正文约 $0.60，合计约 $4.80。这个计算只覆盖第 7.7 节固定选项，不包含额外尝试、其他项目共用额度或 Agent 模型费用；图片理解和文字推理使用的模型 API 单独计费。[S19]

| 项目 | 本应用默认值 |
| --- | --- |
| 服务商及功能 | 仅 Exa 的两个工具，不自动切换别家或尝试付费模式 |
| 搜索参数 | 固定 `auto`、5 条结果；不给模型提高到超过 10 条的权限 |
| 阅读参数 | 单个 URL、仅 `text`；不启用额外摘要及子页面 |
| 两人共用的本地月度提醒 | 估算使用达到 $8 时提示一次，不发推送 |
| 本地月度停止线 | 本次预计消耗会使累计超过 $9 就拒绝发出；达到 $9 后停止新的联网请求 |
| 付费设置 | 使用免费方案，不绑定支付方式、不主动购买额度、关闭自动充值；维护者检查账号实际配置，应用不调用充值或支付接口 |

$8/$9 是本应用选择的提醒/停止值，留出名义 $1 余量，不是 Exa 官方免费额度。阈值只允许维护者配置，Agent 不能修改配置、用量记录或借改前端解除限制。预算共用于珠珠、小花及 UI 代码任务，不按账号各发一份。

关闭自动充值要使用真正的关闭设置；不能把自动充值的月上限填 0 当成禁用。Exa 当前说明该字段为 0 或留空表示不设充值上限。[S20] 应用阈值只是本地保护，不取代免费账户与付费设置的核对。

**复用请求元数据记账。** 在现有 `runtime/requests/{id}.json` 中保存少量 `web_calls`：调用 ID、工具种类、开始时间、预留金额、返回的成本估算（可选）、提供商请求 ID（可选）和状态。金额以整数微美元计算，避免浮点累积。单队列内先持久化本次预留再发 HTTP；默认搜索预留 7,000 微美元、单页正文预留 1,000 微美元。预留失败就不发送。

响应提供有限、非负的数值型 `costDollars.total` 时，将计入值取预留与返回估算的较大值；缺失、超时、取消或中断就暂保留预留值，不按零处理。这个字段本身也是提供商估算，不是最终账单；实际消耗以 Exa 后台为准。若返回值高于预期，更新累计并提示维护者核对费率，不能继续假定旧价格绝对可靠。[S13][S14]

累计从现有请求元数据计算，不另建数据库、账单服务或通用账本。统计读取失败或已知用量缺失时先暂停联网并提示核对，不能默认为本月零消耗。同一消息重试返回已有任务，不再发送；同一实际调用的状态更新不重复累计。服务重启后仍包含已预留和已完成调用；本地月度窗口内的计费元数据不可随普通请求清理删除，也不能通过 Git 回滚业务数据重置用量。

本地按 `APP_TIMEZONE` 的自然月汇总，只是应用限制，不能假定它与 Exa 赠送额度重置时刻一致。跨月只是换本地统计窗口，不是宣称上游余额已恢复；402 仍如实返回，不自动充值或循环探测。上线核对账号赠送与重置规则；专用 API key 方便区分用途，但同团队其他 key 可能共用额度，本地计数看不到其他程序的消耗。

`bootstrap` 和普通工具回执足够显示提供商、本地估算、提醒线、停止线及不可用原因；文字使用“本应用估算用量”，不能写成“Exa 账号精确剩余额度”。只有额度不足或搜索不可用，不影响本地记录、计划读取和其他已配置的模型能力。真实接入测试也计入额度；不定时搜索、预取网页或为了填充界面消耗免费用量。

## 8. 写入、并发与恢复

### 8.1 v1 只运行一个 Agent 任务

全局单任务队列，珠珠和小花的任务依次执行。代码修改期间，新消息可能排队，但静态页面和已保存计划仍能读取。界面显示排队/处理中，不假装两个任务都在执行。

队列元数据保存为 `runtime/requests/{id}.json`，联网调用记录也复用此处，不用 Redis。v1 只部署一个后端实例，不允许悄悄开多个进程同时写同一目录。第 7.8 节的预算预留随同一队列执行，不建立第二套任务系统。

### 8.2 幂等请求

浏览器发送消息前生成 `client_request_id`，重试沿用同一 ID。后端保存 actor、包含正文及有序附件 ID/内容哈希的请求摘要和任务状态；同一账号同一 ID、相同内容返回已有任务，不再次入队。相同 ID 更换文字、图片或图片顺序返回冲突；不能只比较正文而忽略附件。上传得到的 ID 在消息重试时复用，不因重试再次识图和写入。

Finalizer 对一个请求最多产生一次成功的批量业务提交。请求元数据保存工作区基准 revision 和最终 data commit；相同请求重试直接返回原结果，不重新运行模型或合并副本。确需第二次纠正时使用新的用户请求。

请求状态和 Git 提交都记录服务端生成的 request ID。服务在 commit 后、回执前崩溃，重启可以从该提交恢复“实际已保存”的状态，不靠重新调用模型猜测。

### 8.3 一次数据提交

采用单写者和 Git 已提交快照，不建设通用事务引擎：

1. 宿主从当前 data HEAD `S` 创建独立副本，并将 `S` 持久化到 request。
2. Agent 用原生文件工具修改副本；它不能直接写生产 data-repo。
3. Finalizer 读取相对 `S` 的 diff，拒绝越界、符号链接和文件删除，完整校验 JSON、字段、路径人物/日期、附件引用和上限。
4. Finalizer 覆盖新记录的 `recorded_by`、request ID 和时间，将本请求压成一次 commit。
5. 校验生产 HEAD 仍为 `S` 后才 fast-forward 合并；成功后由宿主返回 revision 和保存回执。

一次页面请求先固定一个 commit SHA，再用这个 SHA 读取所需文件。不能读一半 HEAD 旧版本、一半 HEAD 新版本，也不能通过文件监听把尚未提交的临时数据显示出去。

提交失败时，保存诊断信息并恢复本次触碰的文件；新建文件只清理本次明确创建的路径，不运行全仓库 `git clean` 或无条件 `reset --hard`。

启动时检查运行中的请求、未完成修改和 Git 状态。存在未提交文件时按 request 清单隔离并恢复；无法判断的异常停止写入并提示维护者，不自动重建空仓库。中断的模型任务标为 `interrupted`，不自动重复执行有副作用的步骤。

此设计避免向前端暴露半完成的多文件修改，但不能替代磁盘可靠性和异机备份。

### 8.4 路径和文件边界

所有路径必须在预定义根目录内；拒绝绝对路径、`..`、符号链接和越界解析。数据写入仅允许 people、plans、logs、memory、exercises 和 ui.json 的约定路径。

不允许 Agent 写 `.git`、`.gitconfig`、hooks、`.gitattributes`、扩展脚本或凭据。Git 命令使用参数数组调用，提交路径白名单化，禁用来自可写目录的 hooks，不能拼接模型生成的 shell 字符串。

写入前检查文件大小、条目数量和数值格式；未知字段和单位应返回清楚的错误。不要为了“容错”把明显不合法的记录悄悄截断成看似合理的数据。

## 9. 最小 HTTP 接口

保持少量接口，不建设全量资源 CRUD。认证、异常响应、类型由现有后端能力和共享契约实现。

| 方法与路径 | 用途 |
| --- | --- |
| `POST /api/login`、`POST /api/logout` | 两个固定账号登录、退出 |
| `GET /api/bootstrap` | 当前身份、时区、共享状态、前端版本、图片上限、联网能力及本地月度预算状态 |
| `GET /api/day?date=YYYY-MM-DD` | 固定 revision 的计划和实际日志 |
| `GET /api/thread` | 当前账号的当前会话记录 |
| `POST /api/messages` | 创建幂等 Agent 任务，返回 request ID |
| `GET /api/requests/:id` | 查询状态、终态回执及结果 |
| `GET /api/requests/:id/events` | SSE 流式消息与工具状态 |
| `POST /api/requests/:id/cancel` | 停止模型调用和可中断检查 |
| `POST /api/uploads` | 每次 multipart 上传一张图片，返回不透明附件 ID、MIME、尺寸和受保护读取路径 |
| `GET /api/uploads/:id` | 鉴权后读取图片，不允许指定服务器路径 |
| `POST /api/ui-jobs/:id/publish` | 对指定候选版本确认发布 |
| `GET /ops`、`POST /ops/rollback` | 独立恢复入口 |

消息请求示例：

```json
{
  "client_request_id": "browser-generated-uuid",
  "text": "帮小花记录今天的午餐，和昨天一样。",
  "attachment_ids": []
}
```

后端根据登录身份记录这是谁发起的，不能从请求正文接受 `recorded_by`。`text` 或 `attachment_ids` 至少一个非空；附件必须存在、已完成校验并且当前账号有权使用。受保护的附件读取路径仅用于浏览器显示，模型输入由后端读取字节构造。

`GET /api/thread` 还原消息时带回原附件引用和真实来源结果；会话侧的关联信息复用现有 request 元数据或 SDK 支持的消息元数据，不另建聊天数据库。联网工具仅由服务端 Agent 调用，不新增公开的 `/proxy?url=` 接口，也不新增账单 API。

`bootstrap` 的联网状态包括 `provider: "exa"`、是否配置、不可用原因、本地统计月份、估算累计及提醒/停止阈值；不暴露密钥和另一人的查询正文。预算拦截和提供商错误通过现有 `tool_result` 回执返回，不能让前端绕过后端直接调用 Exa。

SSE 使用少量事件：`status`、`text_delta`、`tool_result`、`data_committed`、`ui_preview`、`done`、`error`。对外使用本应用事件形状，不把 Pi 的所有内部类型透传给页面。

SSE 断开不等于任务失败，也不触发再次提交。重连后先查询 request 状态和当前 thread 快照；v1 不实现持久化逐 token 事件回放。反向代理关闭这类响应的缓冲，并设置合适的超时。

取消操作只停止后续工作，已经成功提交的数据不会自动撤销。需要撤销时单独提交新的请求。

另一个人的日志更新，v1 在页面重新获得焦点、切换日期、当前任务结束时刷新；不建设实时协作协议。

## 10. Agent 修改前端

### 10.1 两类修改

已有配置能力通过 `ui.json` 修改，直接走数据提交。需要新增组件、布局或交互时修改 React 源码。两者共用同一个对话入口，不做独立编程工作台。

### 10.2 允许的代码范围

运行中的 Agent 可以读取前端、只读 API 契约和产品说明；可以修改 `web/src/` 中的页面、组件和样式，以及经检查的 `web/public/` 资源。不能修改 server、shared 契约、固定测试、构建脚本、依赖清单、lockfile、可信提示词、鉴权和发布代码。

v1 不给任意宿主机 Bash，也不允许 Agent 在线安装新依赖。现有组件无法满足的新增依赖由维护者审核并更新构建环境。这不妨碍 Agent 使用现有依赖完成前端编辑和反复调试。

初次建设项目的开发者可以实现这些服务端能力；上面限制针对建成后在 App 内运行的 Agent，不能误解为初次开发也不许创建后端。

### 10.3 修改流程

1. 从当前生产 main 创建独立 app 副本；Agent 用隔离的 Pi 原生工具自行浏览、编辑、运行 Git 和检查。
2. 模型结束后，Finalizer 只提取 `web/src` 和 `web/public` 的 diff；其他路径标记为不可发布，不进入生产。
3. Finalizer 将允许 diff 应用到唯一 Git worktree，再导出不含 `.git`、凭据和个人数据的临时目录。
4. 临时容器使用固定依赖运行 typecheck、测试、build 和浏览器冒烟检查。
5. 检查失败，返回真实错误，Agent 继续修改；达到任务预算则停下报告未通过。
6. 检查通过，保存候选源码 revision、构建产物哈希、检查结果和截图，提供预览。
7. 用户确认指定候选后，服务端执行发布；期间源码变了就必须重新检查。发布和回滚也进入同一任务队列，不能绕过单写者规则。

Git worktree 适合保留独立候选工作树，但它仍和主仓库共享 Git 管理数据，不是运行不可信代码的安全沙箱。[S6]

### 10.4 构建沙箱

常驻服务负责模型请求和 Finalizer；Pi 原生工具与实际代码检查都进入 rootless Podman。工具容器只挂载隔离 app/data 副本、可信 `AGENTS.md` 和本轮只读 inbox；检查容器只看到导出候选与固定依赖。两者都不挂载生产 data-repo、runtime 会话、密钥、生产主仓库 `.git` 或任何容器引擎 socket。

关闭网络，使用非 root 用户，移除不必要的 capabilities，设置进程数、内存、CPU、执行时间与输出上限。依赖在维护者准备镜像时安装，任务期间不联网装包。Podman 提供这些运行约束，但配置和挂载仍必须实际验证。[S7]

Git、审批、产物发布由受信任的服务端逻辑执行，不执行候选代码提供的部署脚本。浏览器测试同样只使用演示数据和测试账号，不带生产 Cookie。

代码编辑工具和检查工具没有把模型或 Exa 密钥传进候选代码执行进程。Agent 可经受信任后端的 `web_search/web_read` 查开发文档，再修改源码；该能力不向候选代码开放网络。仅在 system prompt 中要求“不读密钥”不构成边界。

### 10.5 预览和发布

预览使用单独 origin，例如 `preview.example.com`，只提供候选前端与演示数据，不连接生产 API、不携带生产凭据。不在生产 origin 的 `/preview/` 下直接运行未批准脚本。

生产 Cookie 仅属于生产 host；写接口核对精确 Origin，不能只认为两个子域就是安全的。预览限制外部连接和表单提交；生产 CSP 由服务端维护，不允许前端源码放宽。Cookie 与 CSP 配置参考官方浏览器文档，但它们不是任意恶意前端的完整隔离或正确性证明。[S8][S9]

v1 的发布只发布静态前端，不迁移数据、不修改后端。对兼容现有 API 的功能开放自修改；需要新服务端接口的功能明确交给维护者，不伪装成已经打通。

发布动作绑定候选 ID、源码 revision 和产物哈希，使用实际用户确认，不接受模型自称“用户同意”。确认后合入 main，并切换到已经检查过的那份不可变产物，不发布另一遍未经核对的构建。

代码 main、运行版本和发布记录可能在异常中暂时不一致，因此 `runtime/deployment.json` 明确保存源码 revision、产物哈希、当前及上个可用版本，采用临时文件加原子替换更新。服务重启按记录恢复，不依据“Git 最新一次提交”猜测现在运行的产物。

保留上一个可用前端版本。发布后的实际页面检查失败时恢复旧产物，报告失败。现有页面和旧静态资源短期保留，避免用户打开着旧页面时资源突然失效。

### 10.6 前端验收

至少检查手机与桌面尺寸：页面可读、无横向溢出、身份选择不串人、动作展开可用、聊天可发消息及停止、工具回执可见、错误状态可恢复。

新增按钮必须具备实际功能，不能用假成功提示占位。build 通过不代表浏览器流程已经通过；没有验证的能力写明“未验证”，不能显示绿色通过。

## 11. Git 的使用方式

### 11.1 数据与代码分开提交

数据仓库只保存结构化业务状态和说明，不包含应用源码、凭据或原始图片；代码仓库不放两人的真实身体数据和聊天。

一条完成的数据请求对应一次有意义的 commit，不按 token、每行 JSON 或每个临时编辑提交。UI 候选在检查完成后提交；代码检查期间的构建产物不放源码仓库。

提交说明避免直接塞入饮食、健康或聊天全文。记录 request ID、操作者、变更类型和日期，便于恢复和排错。

### 11.2 撤销不是重置历史

业务纠正一般直接修改对应条目并新建提交。用户明确要求撤销某次改动时，服务先查看后续是否修改过同样内容；能安全反向应用才生成新的撤销提交，有冲突就请求精确纠正。

Git revert 是创建一个抵消旧修改的新提交，不保证任何历史修改都能无冲突撤销。[S10] 不对共享仓库执行无条件 `reset --hard`，也不把回滚某人一顿饭实现为回退整个数据仓库。

前端紧急回滚先恢复旧产物，再用受控的新提交记录源码回退；不能仅 revert 代码却仍继续服务坏产物。

### 11.3 Git 不是备份或安全边界

本地 Git 和工作文件放在同一块 VPS 磁盘上，并不构成独立备份。文件从当前版本删除，也不意味着历史版本消失。

data-repo 默认不推送公共远程。代码仓库是否设置远程由维护者决定，系统正常运行不能依赖 GitHub/Gitea 在线。

## 12. 登录、安全和基本限制

v1 只有两个固定账号，不做注册、找回密码或邀请系统。维护者在部署时设置高强度凭据，使用每账号独立随机盐和 Node 的 scrypt 派生密码哈希，校验采用合适的恒定时间比较，不自行设计加密算法。[S11]

登录令牌使用足够长度的密码学随机值，服务端在内存中维护令牌摘要到账号、过期时间的映射。v1 服务重启后重新登录即可，不必再建设持久化登录会话库；这不影响 SDK 聊天会话和业务数据恢复。

登录后使用 HttpOnly、Secure、host-only 的 Cookie，并设置合适的 SameSite 与过期策略。会话 ID 不交给 Agent，不存前端 localStorage。登录失败限速，所有状态修改接口检查身份和请求来源。[S8]

两人拥有对称业务权限，不等于可以查看彼此的原始聊天线程。请求 ID、附件 ID、会话 ID 的查询仍需检查当前账号和约定共享范围，不能仅因为 UUID 难猜就省略鉴权。

附件只允许所需图片格式，检查实际类型、大小和像素限制，服务器生成文件名；不接受 HTML/SVG 作为直接内联的用户附件。上传内容和代码文件都可能包含恶意指令，Agent 只把它们当待分析的数据。[S16][S18]

用户图片通过受保护的附件接口提供，不把 uploads 作为公开静态目录。返回固定且匹配的 MIME、`nosniff` 和私有缓存策略；从共享日志引用附件前检查当前账号原本有权使用该附件，防止借创建引用获取权限。共享访问以当前已提交日志/计划的有效引用为准，不能通过搜索对方原始聊天或历史 commit 获取私有附件。按既有维护流程清理过期未引用上传，不能误删现有消息、日志或需保留历史引用的图片；清理属于维护操作，不新增定时清理服务。

公开网页仅由第 7.7 节的工具通过固定 Exa API 读取；VPS 不直接 fetch 模型给出的任意目标，不执行网页 JavaScript，不跟随网页内容运行命令。输入只接受公开 HTTP(S) 地址；拒绝 URL 用户名/密码、localhost、内网/环回/链路本地 IP、内部域名以及本应用生产和预览 origin。私密分享链接、带访问凭据的 URL 不外发；不允许通过 query/path 编码身体日志来绕过资料查询范围。不要把“域名字符串看起来正常”当成 DNS 安全验证；不做代理是本版减少 VPS 内网访问面的主要边界。对固定 Exa API 的请求禁用自动重定向；模型不能覆盖端点、请求头或 Cookie，也不能在失败后调用宿主 curl 直接抓目标页面。[S17]

网页、搜索摘要、图片文字均为不可信资料，不能改变人物身份、工具权限或授权新的数据导出/删除。后端限制可传给搜索服务的字段及长度；Agent 构造脱离个人身份的通用查询，疑似隐私内容不直接发出。恶意内容识别不能仅靠提示词；固定 API、最小出站参数、密钥隔离及越权/注入测试仍须实现。不宣称这些措施能够识别所有隐蔽编码泄露。[S18]

聊天、来源与动作说明统一按不可信 Markdown 渲染，禁用原始 HTML、脚本、iframe 和外部媒体自动加载。来源使用安全的 HTTP(S) 文本链接，新窗口使用适当的 noopener/noreferrer；不要让模型生成的外链图片绕过工具边界自动外发信息。用户已上传图片仍通过鉴权附件组件展示，不受“禁用外部图片”误伤。

敏感请求、Cookie、模型与搜索密钥、图片 Base64 和完整身体日志不进入普通访问日志。模型请求只携带任务需要的内容；自托管应用和文件不代表外部模型请求完全留在 VPS 内。

首次使用说明数据流：所选图片与相关对话会发送给配置的模型提供商，通用查询和公开 URL 会发送给 Exa；前者不会因此自动发给搜索服务。不把用户图片用作搜索服务的图片查询，不为图片识别生成公开分享地址。

任务设置合理的最大模型轮数、工具输出、执行时长和每日模型调用额度；搜索还执行第 7.8 节独立的月度估算停止线。维护者可按首次实测调整，不能让模型自主放宽。达到上限停止相应操作并保留已完成结果，不递归无限修复、重试或换服务商继续消耗。

## 13. 部署与维护

### 13.1 一条默认部署路线

采用现有 HTTPS 反向代理 + systemd 管理的单个 Node.js 服务。代码检查由该受信任服务调用 rootless Podman 执行固定流程，按任务创建和销毁容器，不增加常驻 runner API 或 Docker-in-Docker。

这样模型仍能完成代码修改，但不存在给模型工具挂载宿主机 Docker socket 的需求。Podman 的宿主权限只由固定的服务端检查实现使用，Agent 没有调用任意 Podman 命令的工具。

部署前确认 VPS 支持 rootless 容器所需环境。若沙箱不可用，保留普通计划和日志功能，关闭代码执行并报告原因；不能自动降级为在宿主机执行候选代码。

### 13.2 配置项

| 配置 | 内容 |
| --- | --- |
| `APP_ORIGIN` | 生产站点 origin |
| `PREVIEW_ORIGIN` | 独立预览 origin |
| `APP_TIMEZONE` | 默认 Asia/Shanghai |
| `DATA_REPO`、`APP_REPO` | 两个绝对路径 |
| `RUNTIME_DIR`、`UPLOADS_DIR`、`RELEASES_DIR` | 独立状态目录 |
| 模型提供商、模型 ID、凭据 | 按实际 SDK 版本配置，验收时必须支持图像输入与工具调用；密钥不进 Git |
| `EXA_API_KEY` | 搜索与阅读共用；只在受信任后端读取，不下发浏览器、模型文本或沙箱 |
| `WEB_WARN_USD`、`WEB_STOP_USD` | 本地自然月提醒与停止阈值，默认 8 / 9；前者必须低于后者，只由维护者配置 |
| 两个账号凭据配置 | 部署生成，Agent 不可读取或修改 |
| 构建镜像 | 固定版本或 digest，与 lockfile 对齐 |
| 资源与调用上限 | 单次任务、图片字节/像素/张数、联网超时/次数/正文长度、构建及模型预算 |

只使用一个服务商，不设置 `SEARCH_PROVIDER` 切换器，也不新增深度模式、额外摘要开关或可被 Agent 覆盖的 API base URL。费率估算和来源核对日期保存为维护者可更新的小常量；价格政策变化时重新核对，不从普通聊天改写。

配置缺失时启动报错或明确关闭对应能力，不静默使用硬编码模型、默认密码或共享演示账号。`bootstrap` 如实返回图像输入与联网工具是否已配置及本地预算状态，并附不可用原因；有 key 不代表上游认证、余额或网络已经通过验证。降级时文字对话和已有计划可用，但不能将缺失图片理解或联网的部署宣称为完整 v1。

### 13.3 开发者需要提供的脚本

以下是实现需要交付的 script 契约，不表示本文档包已经包含应用代码：

```text
pnpm dev          本地开发，使用独立测试数据目录
pnpm typecheck    检查前后端共享类型
pnpm test         核心契约、保存、权限和恢复测试
pnpm build        构建服务端和初始前端
pnpm start        启动生产服务
```

已有代码风格检查配置就沿用。不要仅为凑齐脚本清单引入复杂 lint 工具链，也不要让不存在的检查显示为“通过”。

### 13.4 首次上线检查顺序

先锁定依赖并完成 Pi + assistant-ui 最小流式接入，再建立两个空档案和 data-repo 初始提交。配置凭据、origin、时区与目录权限，构建初始版本并通过登录和日志恢复测试。

接着使用虚构标签图片验证真实视觉模型收到了图像内容，并测试恢复会话后图片仍可查看；配置 `EXA_API_KEY`，核对该账号当前免费额度、重置规则和自动充值关闭状态。在 VPS 上实际完成一次 Search 与一次 Contents，核对正文、来源链接、调用费用估算和失败回执；对比后台用量，不只检查配置项是否存在。

用替身验证 $8 提醒、$9 停止、402/429、取消后计数和重启恢复，不为了测试限额真的耗尽免费额度。首次搜索/阅读实测再加入中文训练资料与官方前端文档的少量查询，检查结果是否可用，不把公开榜单分数当成这两个场景已验收。

然后准备固定构建镜像，验证候选代码看不到真实数据与密钥，配置隔离预览，做一次修改、预览、发布和回滚演练。最后确认异机备份恢复可用，再导入两人确认的真实资料。

应用绑定回环或受控内网地址，通过反向代理暴露；未完成认证和 origin 校验前不得公开提供 Agent 接口。

### 13.5 备份与恢复

沿用 VPS 已有的加密异机备份工具，不为本项目写备份平台。至少覆盖两个仓库的 Git 历史、uploads、需要保留的 sessions、运行中的请求及当月联网用量元数据和 deployment.json；同时保存当前及上个可用静态产物，或验证能够从对应源码和固定依赖重建它们。密钥按独立凭据备份流程管理，不复制进业务仓库。

v1 可在固定时段短暂停止应用后备份，避免边写文件边取得不一致快照；不必先实现不停机快照系统。明确保留期限，并定期在另一个目录做恢复演练。

恢复时先取回仓库和附件，验证目标 commit 和 Schema，再启动服务处理 interrupted 请求。模型和 Exa 密钥单独恢复。测试“计划能查看、已保存日志存在、同一 request 不重复执行、已计入的联网调用不丢失”，而不只是检查压缩包能解开。若恢复到旧备份可能漏掉后续联网消耗，应先核对上游用量，再开放搜索；不能以本地记录缺失认定账号没有消耗。

| 编号 | 场景 | 通过标准 |
| --- | --- | --- |

| A06 | 日期、份量或负重口径不明 | 必要追问或明确未知，不静默猜测 |
| A07 | 网络重试同一消息 | 不重复创建餐食、训练组或 Git commit |
| A08 | 两人同时提交消息 | 按队列处理，后任务读取最新 revision |
| A09 | 非法 JSON、越界路径或符号链接 | 拒绝写入，正常页面仍读取旧提交 |

| A23 | 异机恢复 | 仓库、日志、附件和请求恢复行为符合预期 |
| A24 | 上传虚构营养标签并按份量记录 | 真实模型收到图片内容，识别可读数字，程序换算后保存；不是只传文件名 |
| A25 | 图片消息刷新与重启恢复 | 上传图片、文字及来源引用仍可查看；失败/缺失附件明确提示 |
| A26 | 两人附件权限及非法图片 | 未共享附件不越权；共享日志引用验证权限；伪 MIME、超限、SVG、损坏图片被拒绝 |
| A27 | 图中人物/日期不明、纯图片或仅讨论 | 必要追问，模糊数字不猜；不直接记录成已吃或今天测量；估餐标注假设 |
| A28 | 带图片消息重试、视觉模型拒绝 | 相同请求不重复识别或保存；相同 ID 更换图片返回冲突；模型失败不假称看过 |
| A29 | 搜索并读取正文 | 真正执行 Search 和 Contents，检查对应 URL 的提取状态；引用实际 URL，区分片段、正文、缓存来源和截断；fresh 正确映射 maxAgeHours |
| A30 | 联网超时、缺密钥、限额或无结果 | 返回明确失败/不可用，停止于预算内；不伪造来源，不影响已保存计划读取 |
| A31 | 网页/图片含提示注入或目标 URL 越界 | 不提升权限，不把私人记录写进外发查询；拒绝内部地址和应用自身地址，不直接抓取目标 |
| A32 | 根据参考 UI 截图修改前端 | 代码会话真正收到本次参考图，既有检查/预览/发布链路可用；无私图进源码或沙箱 |
| A33 | 联网与构建沙箱边界 | 后端能查公开资料，候选代码仍不能联网或读取模型/Exa 密钥 |
| A34 | 仅记录、读本地计划与重复阅读 | 本地任务不无故搜索；同一任务复用已成功的相同查询/阅读结果，不重复计费调用 |
| A35 | 两人及代码任务接近预算 | 共用一份累计；$8 提醒；下一请求会超过 $9 时 HTTP 未发出；本地记录仍可用 |
| A36 | 修改联网参数或绕过预算 | 不接受模型指定深度模式、超量结果、摘要、子页面、端点或提高额度；不自动充值与切换服务 |
| A37 | 请求中断、重试、重启与跨月 | 预留先落盘；非法/缺失成本不归零；同一调用不重复统计；统计失败先暂停，重启不清零，跨月不伪称上游余额已恢复 |

测试使用临时目录和虚构 fixtures。大多数测试使用模型与 Exa 响应替身，不消耗真实调用；用量估算、计费模式、错误码和崩溃边界也用替身验证。发布前单独运行少量带明确预算的真实 SDK 图像输入、Search 与 Contents 接入测试。测试图片中的标签数值应有已知期望，但文件名和文字提示不包含期望答案，不能以模型回答了一段文字就判断识图通过。

真实 API 测试未运行或被 VPS 网络阻断时，记录为未验证，不由 mock 通过代替集成通过。A31 的攻击样本通过不等于已证明抵御所有提示注入。

单元测试优先覆盖身份、单位、Schema、幂等、路径、附件权限和统计；端到端覆盖“图片记一餐”“搜索后阅读并带来源回答”“参考图改界面并回滚”三条完整流程。不追求为了覆盖率数字而制造大量低价值测试。

## 15. 实施顺序

### 阶段一：能看

建立工程、两账号身份、文件契约、初始 Git 提交和“今天”页面。用虚构数据验证双人视图、餐食与动作细节；实际数据目录保持空档案。到此即使没有模型，也能正常阅读保存的计划。

### 阶段二：能聊、能记

接通 Pi、assistant-ui、单任务队列和请求状态。实现隔离工作区、Pi 原生七工具转发、宿主 Finalizer、文件校验、Git 回执与会话恢复，同时接通附件上传、受保护读取与视觉模型输入，以及 Exa Search / Contents 两个联网工具和共用月度用量保护。通过两人代记、重试去重、中断恢复、识图记餐与真实来源测试后再接入真实日志；不新增图片页或研究页。

### 阶段三：记得正确

增加三份长期记忆、当前上下文注入、偏好更新和普通遗忘。统计使用纯函数。不要顺手增加向量库、自动巩固或无限聊天检索。

### 阶段四：能改自己

实现受控 UI 工作树、固定沙箱检查、隔离预览、明确发布和独立回滚。完成一个真实小功能，例如训练页“显示上次同器械记录”，验证它读取真实接口而非假数据。此阶段属于 v1 必须交付，不以“以后支持”代替。

### 阶段五：能在 VPS 长期运行

完成资源上限、HTTPS、凭据管理、日志脱敏、备份与恢复演练。检查全部验收项后，导入已确认的个人数据并开始实际使用。

各阶段完成一条可运行路径再进入下一阶段，不先生成大量只含 TODO 的文件。

## 16. 明确暂缓

v1 不做完整离线写入同步、复杂 PWA 缓存、多人实时协作、推送通知、自动周报调度、营养数据库爬取、语音通话、动作视频自动纠错、穿戴设备接入、向量检索、多 Agent 委派、可视化 Git IDE、任意后端自修改或自动安装依赖。

图片上传与理解、Exa 公开网页搜索与阅读不是暂缓项。暂缓的是多搜索服务商自动切换、深度研究接口、独立计费后台、通用文件/PDF 处理、专用 OCR 服务、自动视频分析、浏览器代登录、全站爬取和私有网页抓取；遇到不支持内容直接说明限制，不临时叠加新平台。

手机首先使用响应式 Web 页面。断网时不能调用 Agent，界面明确显示未提交；浏览器仍可保留输入草稿，但不能把本地草稿显示成已保存。后续确有弱网记录需求，再专门实现离线队列。

只有实际出现需求才扩展：多人并发写入超过单实例能力时考虑数据库；记忆检索明确不足时考虑索引；现有功能离不开新后端接口时由维护者扩展。不要预先为这些迁移建设抽象层。

## 17. v1 完成的定义

珠珠和小花都能独立登录，看到各自明确的当天饮食和训练；用文字和图片真实保存日志和调整计划；按需搜索、阅读公开资料并展示真实来源；新会话使用正确的长期偏好；通过 Git 追踪与纠正修改；让 Agent 真正修改前端，并完成检查、预览、发布和恢复。

全部状态在 VPS 上可恢复，成功提示有实际工具结果支持。联网采用 Exa 两个工具，落实免费的账号配置核对、本地月度估算与停止线；超额或失败不阻止本地使用。无需另外部署数据库、向量库、Agent 编排服务、搜索服务或管理后台。
